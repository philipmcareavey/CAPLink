Bridge by CAPLink
Accessibility

Accessibility statement

Last reviewed: 9 September 2026

Our commitment

Bridge by CAPLink is built to conform to WCAG 2.2 Level AA. Because a university partner licenses this platform for every one of its students — including students who rely on assistive technology — accessibility is a launch requirement, not an add-on.

Conformance status

This app is partially conformant with WCAG 2.2 AA: most success criteria are met, and known gaps are listed below rather than left undocumented. Conformance has been assessed by manual expert review — a full automated audit tool (e.g. axe-core) requires a Node.js/browser toolchain this project does not currently run with; see the "How this was tested" section for what manual review actually covered.

What's been done

  • A single, visible focus indicator (--focus-ring) on every interactive element, distinct from the platform's ordinary brass accent colour so a focus ring is never ambiguous with plain decoration.
  • Every interactive control in the reference UI is a real <button>, <a>, or form control — never a <div> with a click handler and nothing else, so every action is reachable by keyboard alone (Tab to reach it, Enter/Space to activate it).
  • The rating flow uses a native <dialog> element, which gives focus-trapping, an accessible name, and Escape-to-close for free from the browser rather than a hand-rolled overlay.
  • Custom, non-native widgets — the match-score dial and the star-rating picker — carry explicit ARIA roles and labels (role="img" with a percentage label on the dial; role="radiogroup"/role="radio" with per-star labels on the picker) since neither has a native HTML equivalent that would convey the same information on its own.
  • Colour is never the only signal — every status (open/pending/rejected, permitted/not permitted) is also conveyed in text, not colour alone.

Known gaps

  • Some data-dense screens (the shortlist match-breakdown, local-search results) haven't yet had a full screen-reader read-through — they're built from the same accessible primitives as the rest of the app, but haven't been individually verified with a screen reader.
  • An automated, tool-based audit (axe-core or equivalent) hasn't been run against this codebase — see "How this was tested" below. A manual review is a reasonable substitute but doesn't catch everything an automated scan would.
  • The tab strips (role tabs, login tabs) are real, keyboard-operable buttons, but don't yet carry the full ARIA tabs pattern (role="tablist"/"tab"/"tabpanel") — they work correctly with a keyboard today, this would make their relationship clearer to a screen reader specifically.

How this was tested

Manual expert review against the WCAG 2.2 AA success criteria, plus targeted checks: keyboard-only navigation through every tab of every role (student, business, university admin); visual focus-order and focus-visible verification; a grep-based sweep of the codebase for click-handled non-interactive elements (the one genuine gap found — a message-thread list built from <div>s — was fixed as part of this review, not left for later); and contrast-checking the design-token colour palette. This substitutes for, but is not equivalent to, an automated axe-core scan or testing with real assistive-technology users — both remain open follow-ups.

Feedback

If you encounter an accessibility barrier anywhere in Bridge by CAPLink, please contact your university's careers team, who can raise it with CAPLink directly.
