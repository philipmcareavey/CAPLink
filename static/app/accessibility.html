Bridge by CAPLink
Accessibility

Accessibility statement

Last reviewed: 10 September 2026

Our commitment

Bridge by CAPLink is built to conform to WCAG 2.2 Level AA. Because a university partner licenses this platform for every one of its students — including students who rely on assistive technology — accessibility is a launch requirement, not an add-on.

Conformance status

This app is partially conformant with WCAG 2.2 AA: most success criteria are met, and known gaps are listed below rather than left undocumented. Conformance has now been assessed by a real automated audit (axe-core, run directly in a real browser against every screen of every role — see "How this was tested" below) as well as manual review, not manual review alone.

What's been done

  • A single, visible focus indicator (--focus-ring) on every interactive element, distinct from the platform's ordinary accent colour so a focus ring is never ambiguous with plain decoration.
  • Every interactive control in the reference UI is a real <button>, <a>, or form control — never a <div> with a click handler and nothing else, so every action is reachable by keyboard alone (Tab to reach it, Enter/Space to activate it).
  • The rating flow uses a native <dialog> element, which gives focus-trapping, an accessible name, and Escape-to-close for free from the browser rather than a hand-rolled overlay.
  • Custom, non-native widgets — the match-score dial and the star-rating picker — carry explicit ARIA roles and labels (role="img" with a percentage label on the dial; role="radiogroup"/role="radio" with per-star labels on the picker) since neither has a native HTML equivalent that would convey the same information on its own.
  • Colour is never the only signal — every status (open/pending/rejected, permitted/not permitted) is also conveyed in text, not colour alone.
  • Every form field's label is programmatically associated with its control (<label for="...">), and a group of checkboxes (e.g. "Allowed bands") has a real group heading rather than a <label> wrapping something that isn't one control — found and fixed by the audit below, previously present across roughly 30 fields site-wide.
  • Every text/background colour pairing in the design-token palette meets the 4.5:1 minimum contrast ratio for normal text — four tokens (--slate, --moss, --warn, --danger) were measurably too light when first introduced and have since been corrected; also found by the audit below.
  • Tab strips (role tabs, login tabs) now carry the ARIA tabs pattern (role="tablist"/"tab", aria-selected, aria-controls) in addition to already being keyboard-operable buttons.

Known gaps

  • Heading levels aren't strictly sequential everywhere (a page's one <h1> is sometimes followed directly by an <h4>, skipping levels) — flagged by axe as a best-practice recommendation, not a WCAG 2.2 success-criterion failure. Fixing it properly means adding a real heading-level layer across the whole app rather than a quick patch; left as a deliberate, documented gap rather than attempted piecemeal.
  • Some data-dense screens (the shortlist match-breakdown, local-search results) haven't yet had a full screen-reader read-through with real assistive-technology software — the automated audit below checks the accessibility tree, not what a screen reader actually announces end-to-end.
  • The SAML SSO assertion-consumer flow (a real IdP posting a signed response) has real backend test coverage but no browser-based accessibility check — it never reaches this reference UI directly.

How this was tested

axe-core 4.10.2 was loaded directly into a real Chrome tab (no Node.js/npm needed — this project has neither, so the audit tool came to the browser instead of the other way round) and run against the login screen, both registration forms, and every tab of all three roles (student: Feed, Contracts, Messages, Local Search, My Ratings; business: My Projects including the shortlist and match-breakdown view, Contracts, Messages; university admin: Partnerships including the expanded agreement-management form, Campus Location). Every genuine WCAG-mapped violation the audit found was fixed in the same session, not just logged: unassociated form labels (~30 fields), four design-token colour pairings below the 4.5:1 contrast minimum, a missing page heading, page content sitting outside any landmark region, and — found by the audit turning on itself mid-fix — an invalid ARIA role this same review had briefly introduced while adding the tabs pattern above. Re-running the audit after each fix, on every screen, is what confirms zero WCAG-mapped violations remain; only the best-practice-only findings above are left open. This substitutes for, but is not equivalent to, testing with real assistive-technology users, which remains an open follow-up.

Feedback
